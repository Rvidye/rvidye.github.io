[Arches](https://github.com/Utah-Graphics-Lab/arches) is a cycle-level GPU simulator developed at the University of Utah's Hardware Ray Tracing Lab. It models GPU components such as streaming multiprocessors, caches, memory controllers, and dedicated ray tracing hardware. It also runs **TRaX**, a ray tracer that executes on the simulated hardware.

One thing Arches was missing, however, was a traditional graphics pipeline. We could simulate ray tracing, but we couldn't compare it against rasterization on the same simulated GPU.

That's where my project comes in.

## Building a GPU inside a GPU simulator

My goal is to implement a rasterization pipeline inspired by **NVIDIA's Turing architecture**, using publicly available documentation, whitepapers, and microbenchmarking studies.

Unlike a software rasterizer, where the main concern is producing the correct image, here I'm interested in modeling the hardware itself: how work moves between the graphics units, how shaders are scheduled, where data gets cached, and how many cycles each operation takes.

I've implemented models of the GigaThread Engine, PolyMorph Engines, Raster Engines, and Raster Operations (ROPs), connected through Arches' existing memory hierarchy.

Vertex and fragment shaders execute as **RISC-V threads** on the simulated streaming multiprocessors, while dedicated fixed-function units handle clipping, triangle setup, rasterization, depth testing, and other graphics operations.

One interesting challenge is preserving the correct ordering of graphics operations while letting different parts of the pipeline execute in parallel. Another is moving geometry through the memory hierarchy without introducing unnecessary bottlenecks.

## Does it actually render anything?

Yes! And getting the correct image was the first major milestone.

I implemented a CPU reference rasterizer alongside the hardware simulator, using shared rasterization math to ensure consistent results. The simulated pipeline now produces **bit-exact color and depth buffers** compared to the reference implementation.

I've tested it with scenes including the Cornell Box, Šibenik Cathedral, and Sponza.

## Some interesting results

With a functional pipeline, I started investigating its performance. All the following measurements use the simulated RTX 2080 configuration at 1024 × 1024.

| Scene | Rasterization | Ray tracing (TRaX) |
| --- | ---: | ---: |
| Cornell Box | 66,652 cycles | 380,762 cycles |
| Šibenik | 243,684 cycles | 401,367 cycles |
| Sponza | 1,551,091 cycles | 509,956 cycles |

The rasterizer is faster on the Cornell Box and Šibenik, but **roughly 3× slower than ray tracing on Sponza**.

The main reason is that my current pipeline doesn't support early depth rejection, so it ends up shading almost 7 million fragments for a one-million-pixel image. Features like early-Z, hierarchical Z-culling, and mipmapping become pretty important here.

Another interesting finding came from investigating triangle throughput. At first, I suspected the rasterization units or internal queues were limiting performance. It turns out the actual bottleneck was **L2 cache throughput**.

The rasterizer could theoretically process six triangles per clock, but the memory requests generated by each triangle limited the measured throughput to approximately 2.27 triangles per clock in a synthetic test.

I also ran into some rather unintuitive performance problems involving memory partition interleaving, shader constant loads, and fragment ordering. These are exactly the kinds of architectural details I wanted to investigate with this project.

## Where it stands

The rasterizer is functional, produces correct images, and supports architectural experiments, but there's still a lot to do.

The current model is **cycle-level, not yet validated as cycle-accurate against real GPU hardware**. Some hardware parameters aren't publicly documented, so they need to be approximated, evaluated experimentally, and eventually calibrated against real hardware measurements.

We're hoping to develop this into a more complete research framework for studying graphics pipeline architectures. There aren't many openly available, detailed GPU rasterization simulators, and having one alongside Arches' existing ray tracing hardware could be useful for exploring future GPU designs.

For now, I'm working on improving the hardware models, investigating performance bottlenecks, and adding missing graphics pipeline features.
